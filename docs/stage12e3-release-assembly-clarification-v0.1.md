# Stage 12E-3 Deterministic Release Assembly Clarification v0.1

Status: proposed frozen design clarification; no implementation is contained in
this document.

## 1. Authority and purpose

This clarification freezes the remaining deterministic construction and
persistence rules for Stage 12E-3 research releases. It is governed by, and
must be read with:

- `integrity-reproducibility-spec-v0.1`;
- `integrity-reproducibility-clarification-v0.1`;
- `release-integrity-profile-v0.1`;
- `release-acquisition-clarification-v0.1`;
- `scientific-artifact-identity-closure-v0.1`;
- `identity-stage5-v0.1`; and
- `identity5-release-version-gate-clarification-v0.1`.

The Scientific Artifact Identity sequence through Identity-5 remains
authoritative and unchanged. Stage 12E-3 does not redefine scientific artifact
identity, family/version dispatch, Instrument Acceptance resolution, Stage 12D
manifest binding, or Stage 12E release eligibility.

Every value generated by Stage 12E-3 MUST be one of:

1. fixed by a frozen assembly contract;
2. deterministically derived from an already-governed input; or
3. explicitly supplied by the caller.

Stage 12E-3 MUST NOT invent scientific, environment, dependency, provider, or
provenance metadata.

## 2. Exact physical release output

For a Release Profile whose `release_id` is
`release:<phase>-v<MAJOR>.<MINOR>`, define `release-id-token` as the substring
after the literal `release:`. For example:

```text
release:pilot-v0.1 -> pilot-v0.1
```

The physical output whitelist is exactly:

```text
releases/<release-id-token>/
    artifact-manifest.json
    reproducibility-manifest.json
    release-build.json
```

The assembler MUST NOT generate `release-profile.json`. The complete Release
Profile remains a caller-supplied governing input.

The assembler MUST NOT copy scientific artifacts, rejected raw inputs, an
Environment artifact, governing documents, or schemas into the release
directory. Locators remain references into the explicitly governed source or
storage context. A fourth file in the generated release directory is an
assembly defect.

The assembler does not auto-increment or discover a research release version.
The structurally valid caller-supplied `release_id` is authoritative.

## 3. Generated contract versions and Release Profile treatment

Stage 12E-3 fixes the generated object contract versions to:

```text
Artifact Manifest.manifest_version                 = "0.1.0"
Reproducibility Manifest.reproducibility_version   = "0.1.0"
Release Build Record.build_version                 = "0.1.0"
```

These values identify assembly-object contracts. They do not derive from the
research release version, Source Release Tag, or any scientific artifact
version. The caller cannot override them in Stage 12E-3 v0.1.

`Release Profile.profile_version` remains caller supplied. Stage 12E-3 MUST NOT
construct, repair, or mutate the Release Profile. In particular, it MUST NOT
insert or rewrite `profile_version`, `release_id`, `release_phase`,
`source_release_tag_identity`, `active_artifacts`, `rejected_inputs`,
`expected_artifact_version`, `environment_reference`, or
`enabled_dependency_extras`.

## 4. Artifact Manifest root contract

The generated Artifact Manifest has:

```text
manifest_version     = "0.1.0"
scope                = {"scope_type": "RELEASE"}
canonicalization_id  = "RFC8785-JCS"
digest_algorithm     = "SHA-256"
```

Its `artifacts` array corresponds exactly to the Release Profile
`active_artifacts` whitelist after exact Identity-4 binding. This equality is
an assembly-specific rule and does not alter general Stage 12D semantics.

No selected artifact may be omitted. No unselected artifact may be added.
Extra caller-supplied scientific documents do not become selected, are ignored
by construction, and are not passed as additional manifest-bound documents to
the Stage 12D validation of the generated candidate.

## 5. Selected scientific document resolution

The caller supplies scientific documents keyed by locator. Stage 12E-3 uses
only locators in `Release Profile.active_artifacts` and performs no filesystem
or repository discovery.

For every active entry, the assembler requires the exact triple:

```text
locator + artifact_family + artifact_id
```

to bind the supplied scientific document under the existing Identity-4
contract. Locator is storage/provenance location, not scientific identity.
The assembler MUST NOT resolve by locator alone, derive a locator from an
artifact ID, insert an intrinsic ID, infer a version, or repair a reference.

A missing selected locator, a mismatched family or identity, an ambiguous
selection, or an unknown exact family/version contract is an assembly failure
before write.

The Artifact Manifest locator is exactly the locator declared by the active
Release Profile entry. No release-directory copy is made.

## 6. Selected artifact metadata and derivation

For every selected artifact, the caller supplies assembly metadata keyed by
locator containing exactly the non-derivable Artifact Manifest entry fields:

```text
lifecycle_state
phase_context
```

`lifecycle_state` remains one of the existing schema values:

```text
DRAFT
VALIDATED
FROZEN
RETIRED
```

It is not inferred from a release, validation result, artifact version, tag,
or filename. Stage 12E-3 v0.1 adds no lifecycle eligibility gate and MUST NOT
automatically choose `FROZEN`.

`phase_context` is likewise explicit caller input. Stage 12E-3 does not force
it to equal `Release Profile.release_phase` and does not infer it from artifact
content. Existing schema and validator constraints remain authoritative; any
stronger cross-phase rule is deferred to a separately frozen policy.

Each generated scientific entry is constructed as follows:

| Source | Fields |
|---|---|
| Release Profile | `artifact_family`, `artifact_id`, `locator` |
| Exact scientific contract | `artifact_version`, `schema_id`, `schema_version` |
| Caller assembly metadata | `lifecycle_state`, `phase_context` |
| Deterministic derivation | `content_digest = canonical_sha256(complete scientific artifact)` |

No other entry value is inferred.

## 7. Scientific artifact ordering and the empty-active boundary

Generated Artifact Manifest scientific entries are sorted by the tuple:

```text
(artifact_family, artifact_id, locator)
```

using Unicode string/code-point ordering after schema-valid input has been
established. Release Profile array order does not control physical Artifact
Manifest order and the Release Profile itself is not reordered.

The Release Profile schema permits an empty `active_artifacts` array in
DEVELOPMENT and INSTRUMENT_VALIDATION. That profile remains structurally valid.
However, the existing Artifact Manifest schema requires at least one
scientific artifact. Because Stage 12E-3 also requires exact whitelist equality,
an empty active set cannot produce a valid Stage 12E-3 Artifact Manifest.

Accordingly, an empty-active profile is not assemblable in Stage 12E-3 v0.1.
Construction reaches the existing Artifact Manifest structural failure and
fails before write as `ASSEMBLY_VALIDATION_FAILED`. This is an assembly
capability boundary, not a new Release Profile validity rule and not a new
scientific cardinality rule.

## 8. Rejected input whitelist and metadata

Generated `Artifact Manifest.rejected_inputs` corresponds exactly to
`Release Profile.rejected_inputs`. No rejected input is discovered or inferred,
and no selected rejected input is omitted.

For every selected rejected input, the Release Profile supplies:

```text
rejected_input_id
locator
```

The caller supplies metadata keyed by locator containing:

```text
rejection_class
description
phase_context
```

The assembler fixes:

```text
digest_scope = "FORENSIC_RAW_BYTES"
```

and derives:

```text
forensic_byte_digest = forensic_sha256_bytes(exact caller-supplied bytes)
```

The digest has the form `sha256:<64 lowercase hexadecimal characters>`. It is
computed from exact bytes, not JSON/JCS canonicalization. Classification,
description, and phase context MUST NOT be inferred from bytes, filenames,
locators, or exception text.

Rejected input entries are sorted by:

```text
(rejected_input_id, locator)
```

Rejected raw bytes are not persisted in the release directory.

## 9. Reproducibility limitations

`reproducibility_limitations` remains the existing schema-defined array of
unique bounded free-text strings. Stage 12E-3 creates no limitation taxonomy
and authors no limitation prose.

Limitations are complete caller input. The assembler validates each string,
does not modify or remove a string, rejects duplicates rather than silently
deduplicating them, and sorts valid unique strings by their UTF-8 byte sequence
for generated output.

For PILOT and CONFIRMATORY, missing original distribution provenance for any
dependency is an assembly failure before write. A limitation cannot waive this
rule.

For DEVELOPMENT and INSTRUMENT_VALIDATION, missing original distribution
provenance is permitted only when `reproducibility_limitations` is nonempty.
The assembler does not interpret whether the explicit prose is substantively
sufficient beyond schema validity and nonemptiness, and it does not generate
the prose.

## 10. Provider records

`model_provider_identities` consists of complete schema-shaped records supplied
by the caller. The assembler MUST NOT derive `identity_status`,
`runtime_identifier`, `version_status`, `model_version`, or provider limitation
text from Agent Condition, Model Condition, filenames, runtime inspection, or
other scientific artifacts.

Provider records are sorted by:

```text
(
    agent_condition_id,
    model_identifier,
    RFC8785-JCS canonical bytes of the complete provider record,
)
```

The canonical bytes are a deterministic final tie-breaker only. Existing
validators retain responsibility for referential and scientific consistency.

## 11. Caller-supplied phase projection

Stage 12E-3 does not infer phase subsets or references by traversing a Campaign
or other scientific graph. The caller supplies a complete phase projection
using the exact Reproducibility Manifest fields:

```text
scenario_subset
control_subset
instrument_configuration_id
instrument_acceptance_reference
capability_evaluation_reference
analysis_configuration_id
campaign_id
scheduled_run_ids
run_ids
repetition_identities
```

The assembler copies these governed values into the candidate Reproducibility
Manifest after deterministic ordering. It does not invent alternate field
names, references, or IDs.

No Campaign-set equality or stronger scientific cardinality is introduced.
Proper Campaign subsets remain permitted. Scheduled-run and run arrays are not
assumed to enumerate an entire Campaign unless an existing frozen validator
already requires that relationship.

## 12. Phase minima and deterministic phase ordering

Existing structural phase rules remain authoritative:

- DEVELOPMENT may have empty scenario/control subsets and schema-permitted
  `NOT_APPLICABLE` campaign, acceptance, capability, and analysis references.
- INSTRUMENT_VALIDATION has the same structural minima unless an existing
  frozen validator requires more.
- PILOT requires nonempty active artifacts, nonempty scenario/control subsets,
  a concrete Campaign reference, and a concrete Instrument Acceptance
  reference.
- CONFIRMATORY has the PILOT requirements and additionally requires concrete
  Capability Evaluation and Analysis Configuration references.

The scalar arrays `scenario_subset`, `control_subset`, `scheduled_run_ids`, and
`run_ids` are emitted in lexicographic string order. Schema-required uniqueness
is enforced; inputs are not sorted in place.

`repetition_identities` contains records rather than scalar IDs. It is sorted
by:

```text
(
    repetition_id,
    scheduled_run_id or "",
    run_id or "",
    RFC8785-JCS canonical bytes of the complete repetition record,
)
```

This ordering supplies a total deterministic projection without changing the
record's meaning or adding cardinality.

## 13. Concrete Environment requirement

Both generated Reproducibility Manifest and Release Build Record schemas
require a concrete Environment binding. Therefore every release assembled by
Stage 12E-3 v0.1 requires:

```text
Release Profile.environment_reference = env:<opaque-token>
```

A DEVELOPMENT or INSTRUMENT_VALIDATION Release Profile containing
`environment_reference = "NOT_APPLICABLE"` remains structurally valid as a
Release Profile, but is not assemblable by Stage 12E-3 v0.1. The pure build
operation fails before constructing invalid generated objects with:

```text
ASSEMBLY_ENVIRONMENT_NOT_ASSEMBLABLE
```

It MUST NOT substitute `null`, omit required fields, fabricate `env:unknown`,
or invent a digest.

For an assemblable release, exact equality is required among:

```text
Release Profile.environment_reference
Release Build Record.environment_reference
Reproducibility Manifest.environment.environment_reference
selected Environment.environment_id
```

The selected Environment is a complete caller-supplied scientific artifact and
must itself be selected through an active artifact entry under the ordinary
identity/manifest contracts. Its identity is caller/artifact governed, not
hash-derived. Its content binding is:

```text
environment_content_digest = canonical_sha256(complete Environment artifact)
```

## 14. Runtime environment facts and build mode

The caller supplies already-acquired `RuntimeEnvironmentFacts` and the complete
selected Environment artifact. Stage 12E-3 performs no environment acquisition
or host inspection. Acquisition-only paths such as interpreter or virtual
environment paths do not appear in generated release objects unless a closed
schema requires them; the current schemas do not.

For DEVELOPMENT and INSTRUMENT_VALIDATION the caller explicitly supplies the
build mode, which may be either:

```text
DEVELOPMENT_TOOLING
CONTROLLED_RUNTIME
```

For PILOT and CONFIRMATORY the assembler deterministically fixes the build mode
to `CONTROLLED_RUNTIME`; the caller cannot override it. Every controlled runtime
requires:

```text
system_site_packages_enabled = false
user_site_packages_enabled   = false
```

Stage 12E-3 does not relax controlled-runtime requirements in an earlier phase.

## 15. Release Build Record construction

The Release Build Record is constructed from the Release Profile,
`RuntimeEnvironmentFacts`, and `RuntimeDependencyClosure`. The assembler fixes:

```text
build_version    = "0.1.0"
build_id         = "build:<release-id-token>"
release_id       = Release Profile.release_id
dependency_scope = "FULL_TRANSITIVE_RUNTIME"
```

All runtime facts and dependency fields otherwise come from the explicit
already-acquired records. `build_id` is not caller assigned or hash-derived.

The Reproducibility Manifest binds the build through:

```text
environment.build_identity = Release Build Record.build_id
environment.build_content_digest =
    canonical_sha256(complete Release Build Record)
```

The Release Build Record does not contain its own digest.

## 16. Runtime dependency closure and extras

Stage 12E-3 consumes an already-acquired `RuntimeDependencyClosure` and MUST NOT
rediscover installed packages. The closure must have been acquired for the
exact caller Release Profile and its exact `enabled_dependency_extras`.

`enabled_dependency_extras` comes only from the Release Profile. The assembler
does not infer extras from installed distributions. It validates all consistency
that is represented by the acquired closure and existing public acquisition
consistency APIs. The fact that acquisition was invoked for those exact extras
is an explicit caller/procedure precondition; Stage 12E-3 does not claim to
prove unrepresented acquisition history.

Dependency ordering follows the deterministic order established by Stage
12E-2. If defensive projection sorting is necessary, it uses the same frozen
normalized distribution-name/version ordering and does not establish a second
ordering convention.

PILOT and CONFIRMATORY require original distribution filename and digest for
every dependency. DEVELOPMENT and INSTRUMENT_VALIDATION follow the explicit
limitation rule in Section 9. No phase is silently downgraded.

## 17. Governing documents and schema set

Stage 12E-3 consumes an already-acquired `GoverningDocumentAcquisition` and
performs no governing-document filesystem discovery. The generated
Reproducibility Manifest contains exactly the frozen nine-document registry in
its frozen registry order. Exact-byte content digests remain authoritative; the
assembler MUST NOT alphabetically reorder the registry.

`schema_set` contains exactly the unique schemas referenced by generated
Artifact Manifest scientific entries. Schema records are obtained from the
caller-supplied `SchemaStore`, not repository scanning, and sorted by
`schema_id`. Stage 12E-3 does not add all repository schemas.

The empty-active boundary in Section 7 also prevents an empty generated
`schema_set`, consistent with the existing Reproducibility Manifest schema.

## 18. Source Release Tag and Git provenance

The Source Release Tag must exist before Stage 12E-3 assembly. The caller
supplies already-acquired `GitProvenance` containing exact repository object
format, commit, tree, annotated source tag identity, tag object, and tag target
commit facts required by the closed contracts.

Stage 12E-3 performs no Git subprocess and creates, moves, or deletes no tag. It
requires exact coherence among the supplied provenance,
`Release Profile.source_release_tag_identity`, release phase, and release
major/minor token under the frozen Release Profile rules. It also requires the
source tag target commit to equal the represented source commit, as governed by
the existing acquisition/validation contracts.

The two-tag sequence is:

1. commit scientific/source content;
2. create `research-release-<phase>-v<MAJOR>.<MINOR>` on that source commit;
3. acquire `GitProvenance` for that tag;
4. assemble the three Stage 12E-3 files referencing that source tag;
5. commit the generated release files in a later integrity commit;
6. independently audit the release;
7. compute the Reproducibility Manifest canonical digest; and
8. create the Release Integrity Tag annotation containing exactly
   `reproducibility-manifest-sha256: sha256:<digest>`.

The Source Release Tag therefore does not contain the generated Stage 12E-3
files. Library code in Stage 12E-3, 12E-4, and 12E-5 performs no Git mutation.

## 19. Artifact Manifest and Reproducibility Manifest bindings

The generated Reproducibility Manifest records:

```text
artifact_manifest_locator =
    "releases/<release-id-token>/artifact-manifest.json"
artifact_manifest_digest =
    canonical_sha256(complete generated Artifact Manifest)
```

The Artifact Manifest does not contain its own digest.

The Reproducibility Manifest environment record binds the complete Environment
and Release Build Record as specified above. It also projects the acquired Git
provenance, governing-document records, schema records, dependency records,
phase projection, provider records, and reproducibility limitations without
fabricating values.

The Reproducibility Manifest does not contain its own digest. Its canonical
digest remains external until the operator-created Release Integrity Tag.

## 20. Acyclic digest dependency graph

The frozen digest dependency graph is:

```text
scientific artifact canonical contents ----+
                                            +--> Artifact Manifest --+
rejected exact bytes -----------------------+                       |
                                                                    |
RuntimeEnvironmentFacts --------------------+                       |
RuntimeDependencyClosure -------------------+--> Release Build -----+
release/build metadata ---------------------+                       |
                                                                    |
Environment artifact --------------------------> Environment digest +
governing-document exact-byte digests ------------------------------+
schema records -----------------------------------------------------+
Source Release Tag / Git provenance -------------------------------+
phase/provider/limitation metadata --------------------------------+
                                                                    v
                                                    Reproducibility Manifest
                                                                    |
                                                   canonical digest |
                                                                    v
                                                  Release Integrity Tag
```

The Source Release Tag precedes the generated release files and is represented
only as supplied provenance. No generated object contains its own digest. No
generated object contains the Release Integrity Tag object identity. The graph
is acyclic and has no self-digest.

## 21. Physical JSON serialization

Canonical digest serialization remains RFC 8785 JCS UTF-8. Physical file bytes
are a separate deterministic representation for all three generated files:

```text
encoding       = UTF-8
ensure_ascii   = False
sort_keys      = True
indent         = 2
separators     = (",", ": ")
allow_nan      = False
trailing bytes = exactly one LF
```

The normative operation is equivalent to:

```python
json.dumps(
    obj,
    ensure_ascii=False,
    sort_keys=True,
    indent=2,
    separators=(",", ": "),
    allow_nan=False,
).encode("utf-8") + b"\n"
```

Physical pretty JSON bytes MUST NOT be substituted for JCS canonical bytes in
any content digest.

Stage 12E-3 generates no wall-clock timestamp, current time, hostname,
username, current working directory, temporary path, or extension field.
Output-root location never enters generated JSON.

## 22. Pure build and bounded write APIs

Stage 12E-3 exposes two separate public operations:

```text
build_research_release(...)
    -> BuiltResearchRelease

write_research_release(
    built_release,
    *,
    output_root,
)
```

`build_research_release` is pure and performs no filesystem write, discovery,
acquisition, Git operation, or subprocess. Its explicit caller inputs are:

- a complete Release Profile;
- scientific documents by locator;
- selected-artifact assembly metadata by locator;
- rejected raw bytes by locator;
- rejected-input assembly metadata by locator;
- a `SchemaStore`;
- `GitProvenance`;
- `GoverningDocumentAcquisition`;
- `RuntimeDependencyClosure`;
- `RuntimeEnvironmentFacts`;
- the complete selected Environment artifact;
- a complete phase projection using the exact schema fields;
- complete provider records;
- complete reproducibility limitations; and
- an explicit build mode for DEVELOPMENT or INSTRUMENT_VALIDATION; PILOT and
  CONFIRMATORY derive `CONTROLLED_RUNTIME` from the frozen phase rule.

Bounded immutable dataclasses SHOULD group selected-artifact metadata,
rejected-input metadata, and phase projection rather than collapse unrelated
values into an untyped miscellaneous mapping. Grouping MUST NOT introduce
hidden defaults or additional semantic inputs.

`BuiltResearchRelease` is an immutable/slotted result containing at least:

```text
release_id
release_id_token
artifact_manifest
reproducibility_manifest
release_build_record
artifact_manifest_bytes
reproducibility_manifest_bytes
release_build_bytes
```

Returned records must be isolated from later caller mutation. Repeated pure
builds over equal governed inputs produce equal objects and byte-identical file
payloads.

## 23. Assembly error model

Assembly construction and write failures use a dedicated
`ReleaseAssemblyErrorCode` and `ReleaseAssemblyError`, not Identity-5
`ReleaseValidationErrorCode`. The Stage 12E-3 v0.1 assembly codes are exactly:

```text
ASSEMBLY_INPUT_INVALID
ASSEMBLY_INPUT_MISSING
ASSEMBLY_ENVIRONMENT_NOT_ASSEMBLABLE
ASSEMBLY_DEPENDENCY_PROVENANCE_INCOMPLETE
ASSEMBLY_VALIDATION_FAILED
ASSEMBLY_DESTINATION_EXISTS
ASSEMBLY_WRITE_FAILED
```

No additional assembly code is introduced without a separately justified
contract change.

When a candidate object fails an existing validator,
`ASSEMBLY_VALIDATION_FAILED` retains/exposes the immutable underlying
validation findings or results with their original codes and paths. Detailed
Stage 12D, Identity-5, Reproducibility Manifest, schema, and release-build
findings are not translated into parallel bespoke assembly taxonomies.

## 24. Pre-return validation composition

The pure build operation validates completely, in this order, before returning:

1. structurally validate the complete Release Profile with the existing
   Release Profile schema and schema-validation API;
2. validate profile/source-tag phase and major/minor coherence;
3. validate completeness and phase-conditional requirements of all explicit
   assembly inputs;
4. resolve exact selected scientific artifacts under existing identity
   contracts;
5. construct the candidate Artifact Manifest from exactly the selected set;
6. call public `validate_artifact_manifest()` over the selected candidate
   document/byte projections;
7. call public `validate_release_artifact_version_gates()` without duplicating
   Identity-5 logic;
8. construct the candidate Release Build Record;
9. structurally validate the Release Build Record;
10. call public `validate_release_build_consistency()` and enforce the frozen
    phase/original-distribution rules;
11. construct the candidate Reproducibility Manifest;
12. call public `validate_reproducibility_manifest()` with its exact explicit
    trusted inputs;
13. serialize all three generated objects deterministically; and
14. return an immutable `BuiltResearchRelease`.

No write occurs before every applicable validation succeeds.

Initial Release Profile structural validation reuses the existing schema API.
Identity-5 remains the authority for the later composed release-selection and
version-gate check; the assembler does not create competing Release Profile or
Identity-5 semantics.

Stage 12E-3 reuses public Stage 12D, Identity-5, acquisition-consistency, schema,
and Reproducibility Manifest APIs. It MUST NOT import cross-module private
resolution helpers or reconstruct intrinsic identity, exact schema binding,
canonical digest validation, or dependency acquisition logic.

## 25. Write destination and no-partial-output model

`write_research_release` receives only a successfully built immutable bundle
and an explicit `output_root`. Its final destination is:

```text
output_root/releases/<release-id-token>/
```

The writer may create the bounded `output_root/releases/` parent when absent.
If the final release directory already exists, it fails closed with
`ASSEMBLY_DESTINATION_EXISTS`. It MUST NOT overwrite, merge, delete, or update
an existing release directory.

The write sequence is:

1. confirm the final destination does not exist;
2. create a uniquely named sibling temporary directory beneath
   `output_root/releases/`;
3. write and close/flush all three fixed file payloads;
4. verify the temporary directory contains exactly the three whitelisted files;
5. atomically rename the temporary directory to `<release-id-token>`.

If a write or rename fails, the final release directory MUST NOT exist. The
writer may clean only the temporary directory created by that invocation and
must not modify unrelated paths. Such a failure uses `ASSEMBLY_WRITE_FAILED`.

## 26. Determinism and input immutability

For identical governed inputs, repeated calls to `build_research_release`
produce byte-identical values for all three generated files. Writing one built
bundle to separate temporary output roots produces byte-identical three-file
release contents.

Neither build nor write mutates caller inputs. Prohibited mutations include
artifact editing, ID or version insertion, reference repair, locator rewriting,
metadata normalization in place, list sorting in place, dependency mutation,
Environment mutation, Release Profile mutation, and document removal.

## 27. Stage ownership and operator procedure

The remaining implementation stages are:

- Stage 12E-3: deterministic in-memory release construction and bounded
  filesystem persistence;
- Stage 12E-4: read-only release-integrity audit orchestration over generated
  objects/files, independently re-running and binding the frozen validators and
  digest closure; and
- Stage 12E-5: fixed synthetic release corpus, regression closure, and
  implementation freeze/tag for the release-integrity implementation.

Stage 12E-4 and Stage 12E-5 do not create actual research-release Source or
Integrity Tags. Source/integrity Git commits and tags are explicit operator
procedures around the validated library workflow. Implementation-stage tags
such as `identity-stage...` are distinct from research-release tags.

## 28. Claims boundary

Stage 12E-3 establishes only deterministic construction and persistence of a
research-release package from explicit governed inputs that satisfy the frozen
identity, integrity, manifest, release-selection, dependency, environment, and
provenance contracts.

It does not establish scientific truth, artifact authenticity beyond supplied
evidence, signature or trust validity, cryptographic security, model
containment, or operational Pilot/Confirmatory validity.

Stage 12E-3 MUST NOT edit scientific artifacts, insert intrinsic identities,
modify versions, repair manifests, rewrite Campaign references, regenerate
scientific outcomes, run models or agents, or execute Pilot/Confirmatory work.
Missing required metadata is a pre-write failure.

## 29. Compatibility conclusions

A complete audit against the governing artifacts and the four release schemas
establishes:

- generated object versions `0.1.0` satisfy their schemas;
- explicit lifecycle and phase metadata cover the non-derivable scientific
  entry fields;
- explicit rejected-input metadata and exact bytes cover every rejected entry
  field;
- provider and limitation values remain explicit rather than fabricated;
- `NOT_APPLICABLE` is preserved as a valid early-phase Release Profile option
  but is rejected before incompatible generated objects are constructed;
- the three-file whitelist is compatible with the release profile because
  locators bind external governed content and the schemas require no scientific
  file copies;
- generated objects have no self-digest and the Source/Integrity Tag sequence
  has no cycle;
- library code requires no Git mutation; and
- scientific, Stage 12D, acquisition, and Identity-5 semantics remain
  unchanged.

The structurally valid empty-active edge is fully bounded by Section 7 and does
not alter Release Profile schema validity.

## 31. Future implementation scope
