# Stage 12E-4 Release Integrity Audit Clarification v0.1

## 1. Status and authority

This document freezes the corrected design for Stage 12E-4. It supplements,
and does not replace or weaken:

- `integrity-reproducibility-spec-v0.1`;
- `integrity-reproducibility-clarification-v0.1`;
- `release-integrity-profile-v0.1`;
- `release-acquisition-clarification-v0.1`;
- `scientific-artifact-identity-closure-v0.1`;
- `identity-stage5-v0.1`;
- `stage12e3-release-assembly-clarification-v0.1`; and
- `implementation-stage12e3-v0.1`.

Current stage:

```text
DESIGN ONLY
```

This clarification authorizes no source, schema, or test modification; no
release assembly or repair; no acquisition; no Git mutation; and no Stage
12E-5 work. Stage 12E-4 implementation requires separate approval.

## 2. Purpose

Stage 12E-4 independently audits a persisted Stage 12E-3 research-release
directory. It re-establishes:

- the exact three-file package layout and ordinary-file policy;
- exact persisted bytes and the strict JSON domain;
- the frozen physical JSON serialization;
- exact generated-object versions and deterministic array ordering;
- exact active and rejected release whitelists;
- Stage 12D artifact and rejected-byte bindings;
- Identity-5 release eligibility;
- Release Build structure, runtime consistency, and dependency projection;
- Environment, source-tag, Git, governing-document, and schema-set bindings;
- phase-specific original-distribution provenance requirements;
- Reproducibility Manifest closure; and
- the successful Reproducibility Manifest canonical digest and operator
  annotation.

The audit performs no repair, acquisition, package mutation, repository
discovery, or Git operation.

## 3. Correct Build field names

The Release Build Record field is exactly:

```text
build_id
```

It is not named `build_identity`. Stage 12E-4 requires:

```text
Release Build Record.build_id
== "build:<release-id-token>"
```

The Reproducibility Manifest Environment record has the distinct field:

```text
environment.build_identity
```

Stage 12E-4 requires:

```text
Reproducibility Manifest.environment.build_identity
== Release Build Record.build_id
```

It separately requires:

```text
Reproducibility Manifest.environment.build_content_digest
== canonical_sha256(complete parsed Release Build Record)
```

Earlier explanatory use of `build_identity` for the identity concept does not
add that field to the Release Build Record. This is a field-name clarification
only; the intended value, generated bytes, and digest semantics are unchanged.

## 4. Exact dependency identity and order

Every dependency ordering check uses the exact acquired/stored strings:

```text
(name, version)
```

The comparison is lexicographic tuple comparison over those exact strings. It
performs no PEP 503 normalization, lowercasing, case folding, punctuation
replacement, underscore/hyphen substitution, whitespace transformation,
Unicode normalization, or version normalization. The phrase `normalized
distribution name` is prohibited for this Stage 12E-4 rule.

## 5. Primary audit subject

The primary and only public v0.1 subject is a persisted `release_directory`
supplied directly by the caller. The audit does not discover releases, select
a latest release, derive a directory from a Git tag, or require a
`BuiltResearchRelease`.

No public in-memory-only `BuiltResearchRelease` audit is defined in v0.1.
Stage 12E-3 construction may be used only to create synthetic test fixtures.

## 6. Exact package whitelist

The release directory contains exactly these three direct children:

```text
artifact-manifest.json
reproducibility-manifest.json
release-build.json
```

Missing or additional direct children fail the audit. In particular, the
package contains no `release-profile.json`, scientific artifact copy, rejected
raw-byte copy, Environment copy, schema copy, governing-document copy, or
arbitrary additional file or directory. No recursive package discovery occurs.

## 7. File-type policy

The auditor uses `lstat` semantics. The supplied `release_directory` must
exist, be a directory under `lstat`, and not be a symbolic link. Each required
direct child must exist, be a regular file under `lstat`, and not be a symbolic
link.

A symlink to a regular file remains invalid. A directory, FIFO, socket, device,
symlink, or other non-regular object in place of a required file is invalid.
The auditor does not follow package symlinks and does not use `Path.is_file()`
as the sole type check.

Package whitelist, root type, missing/extra child, symlink, and non-regular-file
defects use `AUDIT_PACKAGE_LAYOUT_INVALID`. An ordinary required file that
cannot be read uses `AUDIT_PACKAGE_READ_FAILED`. The auditor never changes
permissions or substitutes content.

## 9. Immutable finding model

The audit exposes an immutable, slotted `ReleaseIntegrityAuditFinding` with:

```text
code: ReleaseIntegrityAuditErrorCode
message: str
field_path: str
source: str | None = None
source_code: str | None = None
source_field_path: str | None = None
source_message: str | None = None
```

Each public-validator finding receives its own audit envelope with
`code == AUDIT_VALIDATION_FAILED`. The source fields preserve a deterministic
immutable projection of the original finding taxonomy/type, code value, field
path, and message. The audit does not flatten, discard, or reinterpret the
underlying scientific meaning and retains no mutable alias to source data.

Schema-validation exceptions are projected deterministically using the schema
validation source, the applicable validation keyword or exception category,
the derived JSON pointer, and the bounded original validation message.

## 11. Strict exact-byte JSON parsing

For each required release file, Stage 12E-4:

1. reads exact bytes only after the `lstat` file-type check;
2. decodes strict UTF-8;
3. parses JSON with duplicate-object-key rejection;
4. rejects `NaN`, `Infinity`, and `-Infinity`;
5. rejects malformed JSON; and
6. retains the original bytes for physical comparison.

Malformed UTF-8, duplicate keys, non-JSON numeric constants, or malformed JSON
produce `AUDIT_JSON_INVALID` at the file path. No semantic validation is run
for a file that did not parse. A text-reading path that performs newline
translation before physical comparison is prohibited.

## 12. Physical serialization audit

After strict parse, the auditor independently computes:

```python
json.dumps(
    value,
    ensure_ascii=False,
    sort_keys=True,
    indent=2,
    separators=(",", ": "),
    allow_nan=False,
).encode("utf-8") + b"\n"
```

The result must equal the persisted bytes exactly. Semantic JSON with different
physical bytes produces `AUDIT_PHYSICAL_SERIALIZATION_INVALID` at the file
path. This detects missing or doubled LF, CRLF, compact JSON, incorrect
indentation or separators, unsorted object keys, and escaped-Unicode
representations. The file is never rewritten.

The audit module implements this small serializer independently and does not
import the private Stage 12E-3 serializer. Stage 12E-5 regression fixtures will
detect future drift between the independently constrained implementations.

## 13. Generated-object versions

Stage 12E-4 independently requires:

```text

Reproducibility Manifest.reproducibility_version   "0.1.0"
Release Build Record.build_version                 "0.1.0"
```

An alternate schema-valid semantic version remains invalid for a Stage 12E-3

path with a deterministic message containing the actual and required values.

## 14. Deterministic array ordering

Physical object-key serialization does not sort JSON arrays. Stage 12E-4
therefore compares every frozen array order without mutating it. An order-only
defect uses `AUDIT_DETERMINISTIC_ORDER_INVALID`.

The exact comparators are:

| Array | Comparator |
| --- | --- |
| `Artifact Manifest.artifacts` | `(artifact_family, artifact_id, locator)` |
| `Artifact Manifest.rejected_inputs` | `(rejected_input_id, locator)` |
| `model_provider_identities` | `(agent_condition_id, model_identifier, RFC8785-JCS complete-record bytes)` |
| `reproducibility_limitations` | UTF-8 encoded byte sequence |
| `schema_set` | exact `schema_id` |
| `governing_documents` | exact frozen nine-entry registry order |
| Build and Reproducibility dependencies | exact `(name, version)` |
| `scenario_subset`, `control_subset`, `scheduled_run_ids`, `run_ids` | lexicographic exact strings |
| `repetition_identities` | `(repetition_id, scheduled_run_id or "", run_id or "", RFC8785-JCS complete-record bytes)` |

No comparator normalizes scientific identifiers, dependency names, versions,
or record content. Schema uniqueness checks remain schema-owned.

## 16. Release, Build, source-tag, and Environment bindings

For a structurally valid Release Profile, `release-id-token` is the exact value
after the literal `release:` prefix. Stage 12E-4 requires:

```text

== "build:" + release-id-token

Reproducibility Manifest.environment.build_identity
== Release Build Record.build_id

Release Build Record.release_id
== Release Profile.release_id
```

The Release Profile release ID, phase, Source Release Tag identity, supplied

The following identities must also be exactly equal:

An assembled Stage 12E-3 package cannot use `NOT_APPLICABLE`. A binding defect

## 19. Dependency projection closure

Stage 12E-4 compares both parsed dependency arrays with the supplied governed
`RuntimeDependencyClosure` using the exact Stage 12E-3 projections.

The Release Build projection contains exact `name` and `version`, plus
`distribution_filename` and `distribution_digest` when original-distribution
provenance exists. The Reproducibility projection contains exact `name` and
`version`, plus `distribution_digest` when that provenance exists. Membership,
content, optional-field presence, and values must match the appropriate
projection exactly.

An assembly-specific mismatch not already represented by a public validator
uses `AUDIT_RELEASE_BINDING_INVALID`. Array order is a separate exact
`(name, version)` check. The audit performs no package discovery, resolution,
normalization, or acquisition.

## 20. Phase distribution-provenance rule

The audit independently implements this small frozen policy rather than
importing a private assembly helper:

- PILOT and CONFIRMATORY require original distribution provenance for every
  dependency in the supplied closure. A limitation cannot waive this rule.
- DEVELOPMENT and INSTRUMENT_VALIDATION permit missing provenance only when
  parsed `reproducibility_limitations` is nonempty.

Failure produces `AUDIT_DEPENDENCY_PROVENANCE_INCOMPLETE` at the Release Build
dependency array path. The auditor does not interpret limitation prose.

## 21. Dependency-extras trust boundary

`RuntimeDependencyClosure` is an already-governed Stage 12E-2 acquisition
input. Stage 12E-4 does not independently prove that it was acquired using
exactly `Release Profile.enabled_dependency_extras`, because neither the three
release files nor the current closure record retains sufficient immutable
extras-acquisition evidence.

No finding is emitted solely for that absence. A successful audit establishes
that Build and Reproducibility dependency projections agree with the supplied
governed closure. It does not claim independent proof of the roots/extras that
produced the closure. A future contract may add acquisition evidence without
retroactively changing v0.1.

## 26. Exact schema-set closure

The Reproducibility Manifest `schema_set` identity set must equal exactly the
unique `schema_id` set referenced by parsed scientific Artifact Manifest
entries. Missing and extra schemas are prohibited. A set mismatch uses
`AUDIT_RELEASE_BINDING_INVALID` at
`/reproducibility-manifest.json/schema_set`; ordering is checked separately by
exact `schema_id`.

This narrow assembly-contract audit closes the current validator's allowance
of an otherwise valid extra schema-set entry.

## 27. Governing-document closure

The manifest must contain exactly the frozen nine governing-document records
in registry order. The audit compares membership and public registry metadata
against the supplied `GoverningDocumentAcquisition`. Existing Reproducibility
validation owns exact-byte digest and supplied provenance checks.

An assembly-specific membership defect not otherwise represented uses
`AUDIT_RELEASE_BINDING_INVALID`; an order-only defect uses
`AUDIT_DETERMINISTIC_ORDER_INVALID`. No governing file is discovered or read
from the repository.

## 28. Digest roles and acyclic closure

Digest roles remain exactly:

```text
scientific artifact       canonical_sha256(complete artifact)
rejected raw bytes        forensic_sha256_bytes(exact bytes)
Artifact Manifest         canonical_sha256(parsed Artifact Manifest)
Environment               canonical_sha256(supplied Environment artifact)
Release Build             canonical_sha256(parsed Release Build Record)
Reproducibility Manifest  canonical_sha256(parsed Reproducibility Manifest)
```

Pretty-printed physical file bytes are never substituted for JCS canonical
object bytes. Existing validators own scientific, rejected, Artifact Manifest,
Environment, Build, governing-document, dependency, and Git digest/provenance
edges wherever they already express the defect. Audit-native checks do not
duplicate an equivalent underlying finding.

Closed schemas prohibit generated-object self-digest extension fields. No
generated object contains its own digest or an Integrity Tag object ID. The
digest graph remains acyclic: the external operator Integrity Tag follows the
successful Reproducibility Manifest digest.

## 29. Successful digest and annotation

Only when `findings == ()`, the result contains:

```text
reproducibility_manifest_digest
    = canonical_sha256(parsed Reproducibility Manifest)

integrity_tag_annotation
    = "reproducibility-manifest-sha256: "
      + reproducibility_manifest_digest
```

Both fields are `None` when any finding exists. The audit never inserts the
digest into the manifest and never creates or inspects an Integrity Tag.

## 30. Result and assertion error

The immutable, slotted `ReleaseIntegrityAuditResult` contains:

```text
release_id: str | None
release_id_token: str | None
findings: tuple[ReleaseIntegrityAuditFinding, ...]
reproducibility_manifest_digest: str | None
integrity_tag_annotation: str | None
```

Its `passed` property is defined only as `len(findings) == 0`; no independent
boolean is stored. A structurally valid Release Profile supplies release ID and
token even when a later finding occurs. They may be `None` when Release Profile
structure does not permit safe derivation.

`ReleaseIntegrityAuditError(ValueError)` carries the complete immutable result,
exposes its findings, and has the deterministic message:

```text
research release integrity audit has <count> finding(s)
```

## 32. Audit orchestration and short-circuiting

The deterministic stage order is:

1. structurally validate the supplied Release Profile;
2. `lstat` the release directory and verify the exact package layout;
3. read exact bytes from confirmed ordinary files;
4. strict-parse UTF-8 JSON with duplicate/non-JSON-constant rejection;
5. compare exact physical serialization;
6. structurally validate the three generated objects;
7. check fixed generated versions;
8. check deterministic array ordering;
9. check whitelists and release/Build/source/Environment bindings;
10. call `validate_artifact_manifest()`;
11. call `validate_release_artifact_version_gates()`;
12. check dependency projection and phase distribution provenance;
13. call `validate_release_build_consistency()` with its actual two arguments;
14. check schema-set and governing-registry exact closure;
15. call `validate_reproducibility_manifest()` with the complete projection;
16. only with zero findings, calculate the final digest and annotation.

The audit does not issue speculative downstream findings after a failed
prerequisite. An unreadable manifest is not semantically validated; a
JSON-invalid Build is not passed to Build consistency; and an invalid Release
Profile does not supply inferred release phase, version, or token. Independent
checks may continue only where their prerequisites remain valid.

## 33. Deterministic finding order

Findings use this high-level order:

1. Release Profile structural envelopes;
2. package layout/read;
3. JSON and physical findings in the file order
   `artifact-manifest.json`, `release-build.json`,
   `reproducibility-manifest.json`;
4. generated versions;
5. deterministic arrays;
6. release binding and whitelist checks;
7. Stage 12D envelopes;
8. Identity-5 envelopes;
9. dependency provenance;
10. Release Build envelopes;
11. schema/governing/dependency projection closure;
12. Reproducibility envelopes.

Within audit-native categories, findings sort by `(field_path, code.value,
message)`. A frozen public validator's deterministic ordering is retained
within its source group. Filesystem enumeration order never affects results.

## 34. Immutability and no-write rule

Production Stage 12E-4 writes nothing. It creates no temporary file, audit
report file, cache, repaired copy, or sidecar digest. It never rewrites JSON,
adds a newline, changes permissions, sorts an input array in place, replaces a
symlink, removes an extra file, or updates a digest.

The audit does not mutate package bytes, filenames, caller mappings, Release
Profile, scientific artifacts, rejected bytes, Environment,
`GitProvenance`, `GoverningDocumentAcquisition`, `RuntimeDependencyClosure`,
`RuntimeEnvironmentFacts`, or `SchemaStore`.

## 35. Trusted inputs and claim boundary

The caller explicitly supplies:

- Release Profile;
- scientific artifacts by locator;
- rejected raw bytes by locator;
- `SchemaStore`;
- `GitProvenance`;
- `GoverningDocumentAcquisition`;
- `RuntimeDependencyClosure`;
- `RuntimeEnvironmentFacts`; and
- the selected Environment artifact.

No separate expected provider, limitation, or phase-projection records are
accepted. Their serialized values are checked structurally, deterministically,
and for referential/scientific consistency to the extent the existing public
validators support. The audit does not claim equality to an external operator
intent that v0.1 does not supply.

A successful audit establishes:

> The supplied persisted release package is structurally valid, physically
> deterministic under the frozen Stage 12E-3 representation, and internally
> consistent with the supplied governed scientific artifacts, rejected raw
> bytes, Environment artifact, RuntimeDependencyClosure,
> RuntimeEnvironmentFacts, GitProvenance, GoverningDocumentAcquisition,
> SchemaStore, Release Profile, and frozen release-selection/integrity
> contracts.

It does not establish independent authenticity of caller inputs; independent
proof that the closure was acquired using exactly
`enabled_dependency_extras`; external intent equality for provider,
limitation, or phase projections; scientific truth; signature authenticity;
security; containment; or actual Pilot/Confirmatory correctness.

## 36. No Git or acquisition

The Source Release Tag is represented only by supplied `GitProvenance`.
Stage 12E-4 runs no Git subprocess, performs no tag lookup, accepts no Integrity
Tag input, and creates no tag. It performs no dependency, runtime, governing
document, schema, scientific artifact, or release acquisition.
